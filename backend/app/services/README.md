# `app/services/`

## Responsibility
Business logic, decoupled from both HTTP (FastAPI routes) and raw persistence (Beanie Documents). Each module here is importable and testable on its own — `csv_parser.py` in particular has zero dependency on MongoDB or FastAPI, so it can be unit-tested with plain strings/bytes in and `ParsedExpenseRow` objects out (Phase 3).

## Files
- **`csv_parser.py`** — turns raw uploaded CSV bytes into `list[ParsedExpenseRow]`. Handles: comma vs. semicolon delimiters (`csv.Sniffer`), UTF-8/Latin-1 encoding fallback (common for Brazilian bank exports), header aliasing (`amount`/`valor`/`value` all map to `value`, etc.), and Brazilian-locale numbers (`"1.234,56"`, `"- 2.403,28"`). Negative amounts are auto-categorized as `Payment/Refund` per the approved spec — see `PAYMENT_REFUND_CATEGORY` and the comment in `_parse_row`. `payment_method` is a recognized-but-optional column (not in `REQUIRED_FIELDS`) — a real bank export usually doesn't have one, so a missing value is left `None` here rather than flagged as a parse problem; the `upload-csv` route fills the configured default afterward, since this module deliberately has no database access (see `.github/specs/08_payment_methods.spec.md` §2.3). Never raises on a single bad row; errors are collected into that row's `parse_errors` instead. Only raises `CsvParseError` when the *file itself* isn't readable as CSV at all (empty, no header).
- **`category_service.py`** — case-insensitive category lookup/creation. `find_category_ci` is the single source of truth for "does this category exist" (used by both category creation and expense validation), so the case-insensitivity rule lives in exactly one place. `update_category` toggles mutable fields (currently just `exclude_from_total`, per `.github/specs/03_category_settings.spec.md`) and raises `CategoryNotFoundError` for a missing/malformed id. `seed_default_categories` takes `Iterable[dict]` entries (`{"name": ..., "exclude_from_total": ...}`, matching `default_categories.json`'s shape), not plain names.
- **`payment_method_service.py`** — mirrors `category_service.py`'s shape exactly (`find_payment_method_ci`, `seed_default_payment_methods`), plus `get_default_import_payment_method` (the current CSV-import default's name, or `None` — used by the `upload-csv` route's default-fill pass) and `update_payment_method`, which keeps `is_default_for_import` **exclusive**: it clears every other method's flag before setting the target one, and rejects (`CannotUnsetDefaultImportError`) an attempt to set it `False` directly, since that would either do nothing (already false) or leave zero defaults (currently true) — the only supported way to change the default is to set a *different* method's flag `True`. See `.github/specs/08_payment_methods.spec.md`.
- **`expense_service.py`** — expense creation (single and batch), each validating `category` and `payment_method` against `category_service.find_category_ci`/`payment_method_service.find_payment_method_ci` first, plus filtered/paginated listing. `create_expenses_batch` validates every row before inserting any of them (all-or-nothing) and collects *all* row errors (both category and payment-method problems, not just the first), so the frontend's review table can highlight every bad row in one round trip. `update_expense`/`delete_expense` share a `_get_or_raise` helper (`ExpenseNotFoundError` on a missing/malformed id); `update_expense` re-validates `category`/`payment_method` the same way `create_expense` does, since a `PUT` can change either to something invalid. `find_duplicate_keys` powers the CSV import "possible duplicate" flag: given `(date, title, value)` triples from a fresh parse, it fetches existing expenses sharing those dates and returns the subset whose title also matches case-insensitively — deliberately kept out of `csv_parser.py` since it needs the database, unlike the rest of that module. `get_category_summary`/`get_monthly_summary` run real MongoDB `$group` aggregations over a date range, unpaginated — back the Reports view (`.github/specs/06_category_reports.spec.md`, `.github/specs/07_monthly_summary.spec.md`); unlike `list_expenses`, a fixed row limit doesn't fit a summary that needs to cover the whole selected range.

## Why a separate service layer
Routes in `app/api/` stay thin (parse request -> call service -> map result/exception to HTTP status), and the actual logic isn't tied to FastAPI's request/response cycle. That's what "standalone, testable in isolation" (project Rule 5) means in practice here: you can call `csv_parser.parse_csv(some_bytes, filename="x.csv")` from a plain pytest test with no server or database running.
