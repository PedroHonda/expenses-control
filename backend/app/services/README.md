# `app/services/`

## Responsibility
Business logic, decoupled from both HTTP (FastAPI routes) and raw persistence (Beanie Documents). Each module here is importable and testable on its own — `csv_parser.py` in particular has zero dependency on MongoDB or FastAPI, so it can be unit-tested with plain strings/bytes in and `ParsedExpenseRow` objects out (Phase 3).

## Files
- **`csv_parser.py`** — turns raw uploaded CSV bytes into `list[ParsedExpenseRow]`. Handles: comma vs. semicolon delimiters (`csv.Sniffer`), UTF-8/Latin-1 encoding fallback (common for Brazilian bank exports), header aliasing (`amount`/`valor`/`value` all map to `value`, etc.), and Brazilian-locale numbers (`"1.234,56"`, `"- 2.403,28"`). Negative amounts are auto-categorized as `Payment/Refund` per the approved spec — see `PAYMENT_REFUND_CATEGORY` and the comment in `_parse_row`. Never raises on a single bad row; errors are collected into that row's `parse_errors` instead. Only raises `CsvParseError` when the *file itself* isn't readable as CSV at all (empty, no header).
- **`category_service.py`** — case-insensitive category lookup/creation. `find_category_ci` is the single source of truth for "does this category exist" (used by both category creation and expense validation), so the case-insensitivity rule lives in exactly one place. `update_category` toggles mutable fields (currently just `exclude_from_total`, per `.github/specs/03_category_settings.spec.md`) and raises `CategoryNotFoundError` for a missing/malformed id. `seed_default_categories` takes `Iterable[dict]` entries (`{"name": ..., "exclude_from_total": ...}`, matching `default_categories.json`'s shape), not plain names.
- **`expense_service.py`** — expense creation (single and batch), each validating `category` against `category_service.find_category_ci` first, plus filtered/paginated listing. `create_expenses_batch` validates every row before inserting any of them (all-or-nothing) and collects *all* row errors, not just the first, so the frontend's review table can highlight every bad row in one round trip. `update_expense`/`delete_expense` share a `_get_or_raise` helper (`ExpenseNotFoundError` on a missing/malformed id); `update_expense` re-validates `category` the same way `create_expense` does, since a `PUT` can change it to something invalid. `find_duplicate_keys` powers the CSV import "possible duplicate" flag: given `(date, title, value)` triples from a fresh parse, it fetches existing expenses sharing those dates and returns the subset whose title also matches case-insensitively — deliberately kept out of `csv_parser.py` since it needs the database, unlike the rest of that module.

## Why a separate service layer
Routes in `app/api/` stay thin (parse request -> call service -> map result/exception to HTTP status), and the actual logic isn't tied to FastAPI's request/response cycle. That's what "standalone, testable in isolation" (project Rule 5) means in practice here: you can call `csv_parser.parse_csv(some_bytes, filename="x.csv")` from a plain pytest test with no server or database running.
